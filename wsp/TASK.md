TASK. You are given the weights of a language model, Qwen3-4B-Instruct-2507 (36 decoder layers of width 2,560; grouped-query attention with 32 query heads and 8 key/value heads of size 128, RMSNorm on queries and keys; a SwiGLU MLP of width 9,728 in every layer; RMSNorm; vocabulary 151,936; input embedding and output layer tied). The model is used as a hydrologic-model-calibration agent: in a multi-turn chat it calls three tools, `set_parameters` (11 CREST parameter multipliers), `run_simulation` (runs the EF5/CREST distributed hydrologic model) and `evaluate` (returns NSE, KGE, CC, peak magnitudes and timing lag against USGS observations), and it should iterate until it finds parameters with a high Nash-Sutcliffe efficiency (NSE). Your job is to make it a better calibration agent by EDITING ITS WEIGHTS DIRECTLY: find out what goes wrong inside the network when it calibrates badly and repair that with targeted changes.

You are trial {TRIAL}. Your trial folder is {TRIAL_DIR}; your read-write work folder is {TRIAL_DIR}/work.

HOW IT WILL BE MEASURED. After you finish, your edited model and the unedited model each run the calibration protocol on held-out USGS gages that you never see: the system and user prompt built by src/hydrollm/prompts.py, the three tool schemas in src/hydrollm/tools.py, the loop in curc/eval.py (`calibrate_gage`): greedy decoding (temperature 0), at most 2,048 new tokens per turn, an 8,192-token context in which the oldest messages are dropped when it overflows, at most 100 assistant turns, and up to 3 consecutive "re-emit a valid tool call" hints when a turn contains no parseable tool call (a 4th consecutive failure ends the session). The score for a gage is the best NSE reached in the session, clipped to [-1, 1] as in the project's RL reward (src/hydrollm/verl_reward.py); the primary measure is the mean of that clipped best NSE over the held-out gages (also reported: the unclipped best NSE per gage, the number of simulations run, invalid tool calls and turns without a parseable tool call). The config, tokenizer, chat template, prompts, tools and decoding settings are fixed: only weight values can change (same tensor names and shapes). You never see the held-out gages.

WHAT COUNTS. We want edits that come from understanding the network: find out what goes wrong when it calibrates badly, identify the components responsible (specific neurons, heads, directions or circuits) and change them in a way you can justify with evidence. Repairing a specific failure mechanism is in scope: for example, if the model often wastes turns because it fails to produce a parseable tool call, or if its parameter choices follow some systematic bad habit you can trace to a mechanism, finding and fixing what drives that counts. Out of scope, and refused by save_edit: the final norm (model.norm.weight), the input embedding / output layer (model.embed_tokens.weight, tied to the output layer), and any edit that only multiplies a whole tensor by a constant. Global knobs (making the whole output distribution sharper or flatter) are not what we are looking for, and neither is hard-coding particular parameter values regardless of the gage.

HOW TO WORK.
1. Diagnose first. Read the unedited model's training sessions: how does it fail? (turns without a parseable tool call, invalid calls, sessions that end early, parameter choices that do not respond to the metrics, drifting away from its best parameters, ...). Go after the largest problem you can explain mechanistically.
2. Localize causally. That a component is more active in good turns than bad ones is not enough. Before relying on a component, show that changing it changes the behaviour you predicted (teacher-forced passes are cheap for this: e.g. the log-probability of the first token of a correct tool call at the start of a turn, over hundreds of turns), and try several strengths to see a dose-response.
3. Measure with enough power. There are only 10 training gages and the evaluation is greedy, so end-to-end session measurements are few and noisy: back them up with dense teacher-forced measurements on many turns, use paired "both" passes, and keep an edit only if its effect is consistent rather than driven by one gage. Edits that change a tensor by a fraction of a percent usually have effects too small to see; test strengths large enough to matter and back off if they hurt.
4. Plan your forward passes: for example teacher-forced passes for diagnosis and dose-response, and paired generation passes ("both") to check that an edit actually improves full calibration sessions.
5. Work efficiently: state the hypothesis of each script in its first comment line; load things once per script and save what you will need again; print compact summaries, never whole arrays or whole transcripts (excerpts of at most about 300 characters); keep {TRIAL_DIR}/work/notes.md up to date (findings with numbers, edits tried and their measured effect, the current best edit); before every pass, write the exact current edit and the request to notes.md; keep copies of good edits (for example copy {TRIAL_DIR}/edited to {TRIAL_DIR}/work/best_1/).
